## 실행 순서

```
001  ← 반드시 먼저. 나머지가 쓰는 토큰과 감쇠 블록을 만든다.
 ├─ 002 → 003     (003은 002가 만든 .in 패턴을 그대로 따라 한다)
 ├─ 005
 └─ 006
004 → 007         (같은 파일·같은 구역. 둘 다 pointerdown에 한 줄씩 넣는다)
```

- **001이 선행 조건이다.** 002·003·005·006이 `var(--ease-out)`·`var(--ease-drawer)`를
  쓰고, 네 계획서 모두 001이 만든 `@media (prefers-reduced-motion: reduce)` 블록 안에
  규칙을 덧붙인다. 001 없이 시작하면 곡선이 조용히 무시된다.
- **002 → 003 순서를 지키는 게 좋다.** 003은 002와 같은 `.in` + 강제 리플로우 +
  `transitionend` 패턴을 쓴다. 002를 먼저 하면 003은 베끼는 작업이 된다.
  003 안에 002 없이 진행할 때의 대안도 적어 두었다.
- **004 → 007 순서를 지키는 게 좋다.** 둘 다 `app.js`의 `pointerdown` 핸들러
  같은 자리에 취소 호출을 한 줄씩 넣는다. 따로 하면 충돌한다.
- 001·005·006(CSS만)과 004·007(JS만)은 서로 독립이라 병렬로 진행해도 된다.

가장 레버리지가 큰 건 **002**다. 기사를 읽는 게 이 앱의 주된 동작이고,
서랍은 화면 절반을 차지하는 표면이라 순간이동이 가장 크게 튄다.
시간이 하나뿐이라면 001 + 002만 해도 된다.

## 이 계획서들이 다루지 **않는** 것

- **기존 전환 9곳의 곡선 교체** (`style.css:70,143,267,329,398,448,515,523,530`).
  006이 `transition: all` 한 건만 성능 문제로 처리한다. 나머지는 `review-animations`
  대상이다. 특히 사이드바 접기(`267`·`329`)는 `style.css:322-326`에
  *`transform`을 쓰면 `position:fixed` 말풍선 기준이 깨진다*는 실측 근거가 적힌
  **의도된 결정**이라 함부로 바꾸면 회귀한다.
- **내용 교체 페이드** (`innerHTML =` 약 40곳). 검색 결과·필터 결과는 사용자가
  **읽으려는 데이터**라, 페이드를 넣으면 매 검색마다 첫 줄을 읽는 시점이 늦어진다.
  훑기에서 의도적으로 기각했다.
- **탭 전환 모션** (`app.js:49-50`). 핵심 내비게이션이고, 같은 줄에서
  `window.scrollTo(0,0)`이 함께 돌아 체감 지연만 커진다. 기각.
- **좌측 메뉴 항목의 눌림 반응.** 006이 명시적으로 제외한다.
- **`src/`** (수집·필터·인사이트). 화면이 없다.
