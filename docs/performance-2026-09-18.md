# 배포 사이트 성능 개선 — 2026-09-18

## 확인한 병목

Railway 배포 사이트의 HTML은 약 0.26초, 캐시가 없는 검색 API는 약 9.86초였다. 반복 검색은 약 0.25초로, 화면 파일보다 최초 DB 조회가 주된 병목이었다. 규정 목록은 약 1.2초, 주간 브리핑은 최초 요청 약 2.7초였다. 배포 응답에는 이미 gzip 압축이 적용되어 있었다.

Railway 응답의 지역 표시는 `us-west2`, Supabase 연결 호스트의 지역은 서울(`ap-northeast-2`)이었다. 서버 지역 변경은 사용자가 직접 진행한다.

제목·요약의 부분 일치 조건과 키워드 근거 조회를 OR로 묶은 검색은 PostgreSQL 실행 계획에서 전체 자료를 순차 조회했다. 기존 제목·요약 부분 GIN 인덱스는 이미 존재하고 유효했다.

## 적용한 변경

- 검색의 제목·요약·키워드 일치 ID를 각각 조회한 후 UNION으로 합쳐 중복을 제거한다. 날짜·주제·통과 여부와 정렬 기준은 유지한다. CSV도 같은 검색 조건을 사용한다.
- 검색 건수는 페이지·정렬·페이지 크기와 무관하게 재사용한다. 다른 검색어나 필터는 별도 캐시를 사용한다.
- 브리핑의 현재·직전 기간 건수, 마지막 발행 시각, 일별 추이를 함께 집계한다. 축별 현재·직전 건수도 한 번에 조회한다. 직접 작성된 리뷰가 있으면 이전 다이제스트를 추가로 조회하지 않는다. 한국 시간 날짜 경계와 동일 경과시간 비교를 유지한다.
- 규정 목록은 누적 건수 조회 전에 표시한다. 전체 기간에서는 같은 총건수를 다시 조회하지 않는다. 늦게 도착한 이전 필터 응답을 무시하며, 목록 요청 실패 시 다시 시도할 수 있다.
- 버전이 붙은 공개 정적 파일에 `Cache-Control: public, max-age=3600`을 적용한다. HTML은 계속 재검증하고, 모든 JS·CSS 내용의 해시로 파일 버전을 바꿔 새 배포의 변경을 반영한다. API 응답에는 공개 HTTP 캐시를 추가하지 않았다.

## 측정과 검증

로컬 Python 프로세스에서 같은 실제 Supabase DB에 읽기 전용으로 기존/수정 코드를 순서대로 실행한 단일 측정이다. DB 내부 캐시와 연결 예열의 영향이 있으므로 배포 사이트의 최종 응답 시간을 의미하지 않는다.

작성된 주간 리뷰의 SQL 조회는 9회에서 4회로 줄었다. 검색 건수 캐시가 채워진 상태에서 첫 페이지 전체 조회는 0.180초, 2페이지 조회는 0.066초였다.

`python -m pytest tests -q`: 77개 통과. `node --test tests/*.test.cjs`: 40개 통과. 회귀 검증에는 KST 경계, 페이지·정렬 안정성, 검색 중복 제거, 미선별 자료 포함 옵션, 필터별 건수 캐시 분리, 리뷰 집계, 정적 파일 재검증, 규정 목록 요청 경합과 재시도가 포함된다.

## 캐시와 배포

서버 프로세스 내부 캐시는 검색 응답·검색 건수 60초, 브리핑·규정·과제 후보 120초, 기간 목록 300초다. 기존 브라우저 API 캐시 30초는 유지한다. 여러 캐시가 겹치므로 검색 건수는 갱신 후 최대 약 150초, 기간 목록은 약 330초 뒤 반영될 수 있다. 캐시는 프로세스마다 독립적이며 재시작 시 비워진다.

추가 DB 마이그레이션이나 인덱스 생성은 필요하지 않다. 연결 풀 크기와 서버 지역도 변경하지 않았다. 이 코드 변경을 Railway에 새로 배포해야 운영 사이트에 적용된다. 이전 커밋의 Redeploy만 실행하면 수정 코드가 포함되지 않으므로 새 코드가 배포 소스에 반영되었는지 확인한다.

재배포 후 브라우저를 새로고침하고, 최초 검색/다음 페이지/메뉴 재방문, 주간·월간 브리핑, 규정 기간 변경을 확인한다. 최종 속도는 서버 지역 변경 이후 운영 환경에서 다시 측정한다.
